\section{Architecture Trade-Offs and Justifications}

\subsection{Monolithic vs. Microservices Decision}

The choice to implement a **Modular Monolith** rather than microservices architecture merits critical examination:

\textbf{Advantages Realized:}
\begin{itemize}
    \item **Development Velocity:** Single codebase (\texttt{server.js}) accelerated feature implementation. No inter-service communication protocols (gRPC, message queues) to design.
    \item **Simplified Debugging:** Stack traces span the entire request lifecycle in one process. No distributed tracing infrastructure (Jaeger, Zipkin) required.
    \item **Cost Efficiency:** Single Render.com instance (\$0/month on free tier) vs. microservices requiring multiple containers (\textgreater \$100/month).
\end{itemize}

\textbf{Limitations Acknowledged:}
\begin{itemize}
    \item **Scalability Ceiling:** Cannot scale individual modules (e.g., product search) independently. If chatbot API calls become 10× slower due to high traffic, the entire application suffers.
    \item **Technology Lock-In:** All modules must use Node.js. Cannot leverage Python for data analytics or Go for high-performance components.
    \item **Deployment Risk:** A single bug (e.g., memory leak in chatbot module) brings down the entire system.
\end{itemize}

\textbf{Strategic Justification:} For a solo academic project with \textless 1000 expected users, the monolithic approach was optimal. The **modularity** (clear separation between authentication, cart, order modules) provides a **migration path** to microservices if scale demands it.

\subsection{NoSQL (MongoDB) vs. SQL (PostgreSQL)}

The database technology choice significantly impacts data integrity guarantees:

\textbf{MongoDB Advantages Leveraged:}
\begin{itemize}
    \item **Schema Flexibility:** Product schema evolved during development (added \texttt{spec} field, \texttt{category} enum). No\texttt{ALTER TABLE} migrations required.
    \item **Document Model:** Order documents naturally represent aggregation roots (Order + embedded OrderItems), eliminating JOIN overhead.
    \item **JSON Integration:** Seamless serialization/deserialization with JavaScript objects.
\end{itemize}

\textbf{SQL Advantages Sacrificed:}
\begin{itemize}
    \item **Referential Integrity:** MongoDB lacks foreign key constraints. Orphaned cart items (referencing deleted products) require application-level cleanup.
    \item **ACID Transactions:** While MongoDB 4.0+ supports multi-document transactions, they are complex and not used in this project. Stock deduction is NOT atomic across product and order collections.
    \item **Complex Queries:** SQL's \texttt{JOIN}, \texttt{GROUP BY}, window functions are more powerful than MongoDB's aggregation pipeline for analytics.
\end{itemize}

\textbf{Risk Assessment:} The lack of transactional guarantees poses **data inconsistency risks**. For example, if the server crashes between deducting stock and creating an order, stock is lost permanently. Production systems require MongoDB transactions or migration to PostgreSQL.

\section{Feasibility for Real-World Deployment}

\subsection{What Works (Production-Ready Components)}

\begin{enumerate}
    \item \textbf{Authentication System:} JWT-based authentication with bcrypt password hashing meets industry standards. OAuth 2.0 integration is production-grade if CLIENT\_SECRET is properly secured.

    \item \textbf{Admin Dashboard:} Real-time analytics (Chart.js), order management, and inventory updates provide MVP-level business operations support.

\subsection{WooCommerce (WordPress) Comparison}

\textbf{WooCommerce} is an open-source WordPress plugin powering 28\% of online stores \cite{woocommerce2024}:

\begin{itemize}
    \item \textbf{Advantages over Custom Build:} Massive plugin ecosystem (payment gateways, shipping, SEO), established community support.
    \item \textbf{Disadvantages:} PHP-based (vs. modern JavaScript stack), WordPress overhead (bloated admin panel), security vulnerabilities in plugins.
    \item \textbf{Cost:** Free software, but hosting costs \$5-50/month, premium plugins \$100-500/year.
\end{itemize}

\textbf{This Project's Competitive Edge:}
\begin{itemize}
    \item Modern stack (Node.js, MongoDB) vs. legacy PHP/MySQL
    \item AI chatbot integration (WooCommerce requires paid plugins)
    \item 3D product visualization (impossible in WooCommerce without custom development)
\end{itemize}

\subsection{Business Risks}

\begin{itemize}
    \item \textbf{Regulatory Compliance (GDPR, CCPA):} Current implementation lacks:
    \begin{itemize}
        \item Data export/deletion on user request (GDPR Article 17 "Right to be Forgotten")
        \item Cookie consent banners
        \item Privacy policy and terms of service
    \end{itemize}
    
    \textbf{Mitigation:} Integrate GDPR-compliant consent management platform (e.g., Cookiebot).
    
    \item \textbf{Payment Processor Rejection:} Without business registration, cannot obtain Stripe/PayPal merchant accounts.
    
    \textbf{Mitigation:} Operate as demo/portfolio project, not actual commercial venture.
\end{itemize}

\section{Limitations and Future Work}

\subsection{Acknowledged Limitations}

\begin{enumerate}
    \item \textbf{No Automated Testing:} Absence of unit tests (Jest, Mocha) increases regression risk when adding features.
    \item \textbf{Limited Scalability:} Single-instance deployment cannot handle viral traffic spikes.
    \item \textbf{Basic Admin Features:} No bulk product import (CSV upload), no advanced analytics (cohort analysis, customer lifetime value).
    \item \textbf{Rudimentary AI Chatbot:} Context limited to product catalog. Cannot handle complex queries (e.g., "Compare iPhone 15 Pro vs. Samsung S24 Ultra").
\end{enumerate}

The project successfully validates the hypothesis that modern web technologies enable rapid development of feature-rich e-commerce platforms, while also illuminating the substantial gap between academic prototypes and production-ready systems.
